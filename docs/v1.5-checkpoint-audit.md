# V1.5 checkpoint audit

Status: implementation checkpoint, not deployment promotion.

This audit records what the current Rust fixtures prove and what remains for a
deployment-owned cohort. It is the handoff boundary for the next V1.5 slice.

## Proven by repository fixtures

- Stable five-part identity, move/rewrite/tombstone/restore versioning, event
  order, and multiple records per session.
- BLAKE3 complete-record revisions; guarded no-follow discovery; stability
  admission; source ownership; tombstone grace; duplicate-identity rejection;
  unchanged steady scans skip rehash; and durable byte-budgeted scrubbing.
- Held-descriptor validation, atomic replacement protection, and verified
  lease-scoped path materialization with bounded cache ownership/recovery.
- Per-subscription delivery rows, replay/rebuild epochs, pause/resume, selected
  replay sequence, per-record ordering, retries/expiry backoff, dead-letter
  barriers, and conservative blocking of unavailable mutable bytes.
- Idempotent controlled delivery through the fake adapter, plus a reusable
  filesystem evidence adapter that persists provenance-only manifests.
- SQLite online-backup, manifest validation, and restore preserve event and
  outstanding-delivery state. Status and measurement helpers expose the inputs
  needed to record an operational envelope.

`rtk cargo fmt --check`, `rtk cargo clippy --all-targets -- -D warnings`,
`rtk cargo test`, and `rtk git diff --check` passed at this checkpoint (47
tests).

## Not yet proven by fixtures or deployment

- A representative long-running mirror cohort: seed, append/rewrite, scrub,
  and delivery measurements on the target hardware.
- A bounded MemPalace cohort and its provenance/retrieval acceptance checks.
  `MempalaceConsumer` now has a CLI contract and durable receipt proof. A
  bounded deployment pilot, if run, is still not a full-corpus or promotion
  claim. Learned-context authoring remains out of scope.
- A source-identity convergence proof. The current Bookkeeper adapter uses a
  catalog-allocated record ID while a direct MemPalace batch import uses a
  source path by default. A seed followed by Bookkeeper delivery can therefore
  produce competing provenance for one transcript unless both paths adopt one
  deterministic logical source ID.
- A clean archive-search rebuild lifecycle: a fresh consumer subscription
  epoch, a resumable whole-archive candidate, reconciliation of files that
  change during the seed, and an explicit promotion/retirement boundary.
- Consumer filters, metadata-only delivery, and latest-only supersession policy
  for unavailable historical V1.5 revisions. The available safe policy is
  retry or durable block.
- A deployment-owned trigger, status, and recovery contract. Controlled runs
  remain explicit calls; the repository does not install a background worker or
  perform client network transport.

## Next V1.5 slice

First define the deterministic source identity shared by a direct archive seed
and the Bookkeeper adapter, then prove that seeding one session and delivering
it through Bookkeeper does not create a second search source. Next run the
bounded one-shot evidence cohort against the operator-provided mirror: one
small session, one representative large session, then a small allowlisted
cohort. Record the measurement helper outputs, delivery outcomes, emitted
evidence manifests, and provenance checks. Only then design the new consumer
epoch and resumable whole-archive candidate. Promote only if the deployment
evidence satisfies the still-open gates in [proof-plan.md](proof-plan.md).

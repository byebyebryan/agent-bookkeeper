# V1.5 catalog and consumer controller

Status: implementation underway. The shared domain and durable catalog are in
place, along with guarded filesystem discovery, durable scan-state, tombstone
reconciliation, held-descriptor validation, the durable subscription/lease
ledger, and a bounded path-consumer proof harness. Deployment adapters and
operational proof remain pending. See [implementation status](implementation-status.md).

## Outcome

V1.5 turns an existing byte-preserving filesystem mirror into a revision-aware
archive feed for independent consumers. It does not replace the mirror or take
over client transport. It establishes the domain model and consumer boundary
that V2 will retain.

```text
operator-provided raw mirror (read-only)
        |
        v
filesystem source adapter
        |
        v
reconciler -> durable archive ledger -> per-consumer delivery queues
                                            |
                          +-----------------+-----------------+
                          v                                   v
                 evidence/search adapter             learned-memory adapter
```

## Goals

- Detect new, changed, moved, archived, and removed session records without
  hashing every file on every scan.
- Assign a stable logical identity independent of the record's current path.
- Record byte-exact, algorithm-tagged revisions and ordered archive events.
- Deliver revisions to each consumer independently with bounded concurrency,
  retry, pause, replay, and provenance.
- Make a cheap periodic reconciliation scan sufficient for eventual
  correctness while accepting optional event-driven wakeups as an optimization.
- Preserve a clean storage and API seam for V2 service-owned transport.

## Non-goals

- Uploading bytes from workstations.
- Chunking, object deduplication, or a service-owned current projection.
- Parsing sessions into semantic chunks or deciding what downstream systems
  should remember.
- Exactly-once effects inside an external consumer.
- Inferring privacy deletion from a path move or provider archive operation.

## Runtime shape

The initial reference deployment is one service process with bounded internal
workers and an operator-provided durable control directory. A single-node
SQLite database on a filesystem with proven local locking and `fsync` semantics
is the reference persistence layer. SQLite is a deployment choice for the first
implementation, not part of the public consumer contract. Backup and restore
follow [the durability contract](durability-contract.md).

Logical modules are kept separate even when linked into one binary:

| Module | Responsibility |
| --- | --- |
| `core` | Identities, revisions, generations, events, invariants, and state transitions. |
| `catalog` | Durable schema, migrations, transactions, and ordered event ledger. |
| `source-fs` | Read-only filesystem discovery and provider/layout plugins. |
| `reconciler` | Stability checks, hashing, moves, conflicts, and tombstone candidates. |
| `delivery` | Per-subscription queues, leases, settled outcomes, retry, and replay modes. |
| `admin` | Health, readiness, status, pause/resume, reconciliation trigger, and metrics. |

The modules should be library boundaries, not necessarily separate containers.

## Storage classes

| State | V1.5 owner | Recovery class |
| --- | --- | --- |
| Raw mirror bytes | Deployment/operator | Canonical current evidence; read-only to Bookkeeper. |
| Accepted identities, revisions, events, and tombstones | Bookkeeper ledger | Durable archive metadata; losing it loses history and move/delete semantics. |
| Scan fingerprints and stability observations | Bookkeeper catalog | Rebuildable optimization. |
| Consumer delivery and cursor state | Bookkeeper catalog | Durable operational state; backed up for exact restore, or explicitly rebuilt as a new subscription. |
| Consumer indexes and learned context | Consumer | Derived and independently rebuildable. |

The V1 mirror can reconstruct current bytes, but it cannot necessarily
reconstruct earlier locations or deletion observations. The archive ledger is
therefore durable even though some catalog indexes are rebuildable.

V1.5 records historical revision metadata but does not claim immutable
availability of every historical byte revision. Its borrowed external file may
advance after cataloging. V2 canonical object storage is the phase that makes
retained revision bytes an archive guarantee.

## Source configuration

A configured source has:

- `source_id`: stable deployment-scoped identifier for this source adapter;
- `producer_id`: stable producer/device identity represented by the tree;
- `agent_namespace`: provider family, such as `codex`;
- `root`: read-only filesystem root;
- `layout_plugin`: parser for accepted paths and provider session identity;
- `stability_policy`: minimum unchanged observations or elapsed quiet time;
- `deletion_mode`: `disabled` or `guarded`;
- `root_guard`: required marker or stable storage identity whenever deletion
  mode is `guarded`.

Provider plugins may parse metadata needed for identity, but they must not
perform semantic memory extraction. An unsupported or malformed record enters
an explicit conflict/error state and is not guessed into a new identity.

## Domain model

The schema is conceptual; physical table layout may evolve behind migrations.

### Producer

A producer is one authorized origin of records. `producer_id` is stable across
hostname changes and transport upgrades. It becomes the V2 client authorization
scope.

### Record

A record is identified by:

```text
(producer_id, agent_namespace, session_id, record_kind, record_key)
```

`session_id`, `record_kind`, and `record_key` come from a versioned provider
identity schema. The primary single-file transcript uses
`record_kind=transcript` and `record_key=primary`. Current root role and relative
path are mutable location attributes. Moving a record between active and
archived roots does not create a new record. The normative identity and producer
lifecycle rules are in [domain-contract.md](domain-contract.md).

### Revision

A revision describes exact bytes:

- canonical complete-record BLAKE3-256 digest;
- byte length;
- first and last observation times;
- source locator;
- validation state;
- optional provider metadata that is independent of semantic extraction.

Revision identity is `(record_id, byte_length, blake3-256 digest)`. Optional
algorithm-tagged secondary digests support consumer interoperability but do not
change identity. A move with unchanged bytes reuses the revision and emits a
location event.

V1.5 locators have `availability=current_external`. A Bookkeeper
`RevisionReader` opens and retains one guarded file descriptor, streams and
validates the expected bytes from that descriptor, and never asks the consumer
to reopen the mutable source path. Path-only consumers receive a lease-scoped
verified materialization. If the borrowed file no longer matches, the old
locator becomes stale and is never presented as those historical bytes. See
[payload-delivery-contract.md](payload-delivery-contract.md).

### Generation

A generation groups changes observed together and provides an ordered event
boundary. A V1.5 filesystem scan cannot prove that it observed an atomic client
batch, so its generation has `completeness=observed`. V2 later adds native,
client-committed generations with `completeness=declared`.

Consumers must depend on committed record events, not assume a V1.5 observed
generation is a transaction across an entire device tree.

### Event

The ledger has a monotonically ordered sequence. Consumer-relevant event types
are:

- `revision_committed`;
- `location_changed`;
- `record_tombstoned`;
- `record_restored`.

`conflict_opened` and `conflict_resolved` are operator audit events and do not
create ordinary consumer deliveries.

Events refer to immutable record/revision identifiers. Administrative retries
never create a second logical event for the same state transition.

### Consumer and delivery

A consumer has a stable logical ID and one or more subscription epochs. Each
subscription has configuration, capability declarations, delivery policy, and a
logical cursor. Each event creates at most one active delivery row per
subscription, but the delivery may be leased more than once until settled.
Different records may run concurrently; versions of one record are strictly
ordered.

## Reconciliation algorithm

Each source is reconciled independently:

1. Verify source identity. A missing or incorrect source root is unhealthy, not
   an empty archive. Without a configured guard, deletion detection is disabled.
2. Enumerate only provider-approved finalized files. Ignore transport temporary
   names and reject path traversal or unexpected file types.
3. Parse stable record identity and logical location through the layout plugin.
4. Compare a cheap fingerprint—path, size, modification time, and available
   filesystem identity—with the previous observation.
5. If the candidate is new or changed, require the configured stability policy.
6. Stream-hash the stable candidate and re-check cheap metadata before accepting
   the result. If it changed during hashing, discard the result and retry later.
7. Commit new revisions, location changes, or conflicts in one catalog
   transaction and append their ordered events.
8. Create eligible per-consumer deliveries subject to consumer filters and
   backpressure.
9. In `guarded` deletion mode, mark missing records as tombstone candidates only
   after complete guard checks at both ends of the scan. Commit tombstones only
   after the configured time and complete-scan grace. In `disabled` mode,
   absence never becomes a tombstone.

A steady-state scan should do directory enumeration and cheap metadata reads,
not full-file hashing. Periodic reconciliation is the correctness mechanism;
an API wakeup or filesystem notification may reduce latency but cannot replace
it. A separate byte-budgeted integrity scrub eventually rehashes unchanged
records so restored timestamps or same-size drift cannot remain invisible.

## Moves, duplicates, and deletions

- The same session identity at a new path is a location change.
- The same identity and digest at two paths is a duplicate-location conflict
  until the layout plugin or operator resolves it.
- The same identity with two different current byte revisions is a content
  conflict; neither is silently selected.
- Absence after one scan is not deletion. Guarded root identity at scan start
  and end, multiple complete scans, and elapsed grace are required.
- Active-to-archived movement is lifecycle metadata, never a tombstone.
- Privacy deletion is a separate future command and policy, not inferred from
  ordinary source disappearance.

## Consumer delivery contract

Delivery is **at least once until settled**. Exactly-once behavior across
Bookkeeper and an external consumer is not generally possible without a shared
transaction. Consumers or their adapters must therefore be idempotent on:

```text
(subscription_id, event_id)
```

A leased delivery contains:

- event type and monotonically ordered sequence;
- record identity, monotonic `record_version`, and current logical location;
- revision digest, length, and immutable provenance;
- an opaque raw-byte locator resolved by Bookkeeper;
- generation identity and completeness;
- delivery attempt and lease expiry.

The consumer adapter acknowledges success only after the external system has
durably recorded the source revision. Failure or lease expiry makes the event
eligible again. At most one unresolved event is leaseable per subscription and
record, preventing stale revision retries after later moves or tombstones. A
contiguous high-water cursor advances only across explicit advancing outcomes;
dead letters remain ordering barriers, and delivery rows remain authoritative
for gaps.

For a V1.5 `current_external` locator, `RevisionReader` validates the byte length
and digest from one held descriptor. If it has changed, Bookkeeper reconciles the
newer revision. A consumer configured for `latest_only` may mark the unavailable
old delivery `superseded` and receive the latest stable revision; a consumer
that requires every revision remains blocked until a retained payload exists.
This coalescing decision is explicit delivery policy, never a false success.

Consumers declare support for revisions, moves, tombstones, and replay. A
consumer that cannot apply a destructive event is paused with an explicit
unsupported-capability status rather than pretending the event succeeded.
The complete ordered state machine—including `acknowledged`, `superseded`,
`ignored_by_policy`, and `dead_lettered`—is normative in
[payload-delivery-contract.md](payload-delivery-contract.md).

## Backpressure and controlled runs

Policy is per consumer:

- enabled/paused state;
- maximum active leases;
- maximum records and source bytes per batch;
- retry limit, exponential backoff, and dead-letter threshold;
- optional CPU, memory, or load stop conditions;
- allowlist/filter for controlled cohorts;
- maintenance windows where required by the consumer.

Discovery never directly starts unbounded embedding. It appends catalog events;
the delivery scheduler admits bounded work. A large backlog is expected state
and must be visible without being treated as a service failure.

The first real consumer proof should use an empty consumer index and an explicit
input allowlist: one small session, one representative large session, a small
cohort, then a bounded backfill. Each run records source revisions, elapsed
time, source bytes, consumer output count, resource use, and provenance checks.

`rebuild_current` creates a new subscription snapshot of latest available
records and is supported in V1.5. Full byte-bearing `replay_events` is lossless
only for retained V2 revisions; unavailable V1.5 history follows explicit
supersede, metadata-only, or block policy.

## Status surface

The administrative API and CLI should report, without transcript content:

- source health, last complete scan, and next reconciliation;
- files enumerated, candidates awaiting stability, and bytes hashed;
- scrub cursor, bytes remaining, and integrity mismatches;
- conflicts and tombstone candidates;
- latest archive event sequence;
- per-consumer pending, leased, failed, dead-lettered, and acknowledged counts;
- oldest pending age and last successful acknowledgement;
- current resource/backpressure reason when a consumer is paused.

## Failure and recovery

- A service restart resumes from persisted catalog and delivery state.
- A consumer restart or outage expires leases and redelivers safely.
- Loss of scan fingerprints causes a slow re-observation, not duplicate archive
  events, because digest and domain uniqueness constraints remain.
- A borrowed raw file that advances before delivery fails digest validation;
  its event is retried, superseded under explicit policy, or blocked. The old
  bytes are not fabricated from revision metadata.
- Loss of consumer state permits deliberate replay from the archive event
  sequence under a new subscription ID; it is not presented as exact restoration
  of prior acknowledgements.
- Loss of the durable archive ledger requires restoration from its backup;
  current raw bytes alone cannot recreate all historical move and deletion
  semantics.
- A source mount outage blocks that source and never emits bulk tombstones.
- A source without a root identity guard has deletion detection disabled.

## Implementation slices

1. **Core and fixtures:** the shared domain, payload, delivery, and durability
   contracts; SQLite migrations; provider-neutral test layout; and
   invariant/property tests.
2. **Catalog-only observer:** guarded filesystem scan, stability, streaming
   digest, dry-run diff, and status. No real consumers.
3. **Delivery proof:** per-record ordering, settled outcomes, subscription
   epochs, replay modes, backpressure, `RevisionReader`, and an idempotent fake
   consumer with injected failures.
4. **Controlled archive consumer:** a deployment-owned adapter to an empty
   evidence/search index, starting with an explicit allowlist and validating
   each borrowed source revision during consumption.
5. **Operational closure:** metrics, backup/restore of the ledger, tombstone
   grace, conflict tooling, and representative large-record benchmarks.

V1.5 is complete only when these slices pass the gates in
[proof-plan.md](proof-plan.md). V2 protocol work may be prototyped after the
domain model is stable, but V2 cutover depends on this ledger and delivery
contract being proven.
